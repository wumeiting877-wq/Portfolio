## 3. RESOURCE SECRET FIELD AUDIT

### Sensitive Fields Existing

**没有专用敏感字段。** Model、Pydantic schema、Alembic schema 和 development DB 实际列均不存在：

```text
password
secret
api_key
token
access_token
private_key
client_secret
passphrase
encrypted_payload
```

资源 Create / Update schema 使用 `extra="forbid"`，以上额外键会被拒绝。既有 Import 也拒绝 credential-like 表头。

### Important residual risk

`account_identifier` 和 `remark` 是普通可导出、可返回、可写入 Audit before/after 的业务字段。前端当前只通过关键词规则提示“不能填写凭据”，后端资源 API 没有等价内容扫描；因此它们**不是秘密存储边界**，也不能证明历史自由文本绝对没有被误填过秘密。

C1 禁止把这些字段自动迁移到 ResourceCredential。后续只允许新建独立 ResourceCredential，并应在 UI / API 文案中继续明确 `account_identifier` 不是密码。任何真实 Secret 导入必须等待 C1–C5 明确批准。

## 4. User / Employee Mapping

真实关系为：

```text
Employee 0..1 ── 0..1 User
```

- `users.employee_id` 可空，外键指向 `employees.id`，并有唯一约束。
- ADMIN 等系统用户可以没有 Employee，但仍然是可认证的 System User。
- ResourceAllocation 授予 Employee 业务使用关系；登录和安全主体是 User。
- `CurrentUser` 同时携带 `id`（User ID）和可空 `employee_id`。

结论：Credential Grant 必须外键到 `users.id`，不能外键到 Employee，也不能从 ResourceAllocation 自动生成 Grant。ResourceAllocation 只用于 Resource Scope 的第一层判断。

## 5. Auth Reuse

### Current implementation

- 密码采用 `argon2-cffi` 的 `PasswordHasher`；`verify_password()` 已集中在 `app.core.security`。
- 登录由 `authenticate_user()` 复用该验证函数，并检查 ACTIVE / DISABLED / LOCKED。
- 改密也复用 `verify_password()`；密码只保存 Argon2 hash。
- `get_current_user()` 从 Bearer JWT 读取 user_id 后重新查询 User、Role、Employee，并再次检查 User ACTIVE。
- 当前 access JWT 包含 `user_id`、`username`、`role`、`scope`、`exp`；本版本禁止改变该结构。
- 当前没有 recent re-auth、reauth proof、token jti 或服务器端 session。

### Recommended Re-auth Flow

1. `POST /api/auth/re-auth` 必须要求现有 Bearer CurrentUser，输入仅 `current_password`。
2. 直接复用 `verify_password(current_password, current_user.user.password_hash)`；不得把密码传入 Credential Service。
3. 成功后生成至少 256-bit 的随机 proof，仅向前端返回一次；数据库只保存 proof 的 SHA-256 digest、`user_id`、`expires_at`、`created_at`、`revoked_at`。
4. 有效期建议 5 分钟，硬上限 15 分钟；密码修改、用户停用时应使既有 proof 失效。
5. proof 只保存在页面内存，通过专用 header 提交到 Reveal；禁止 localStorage、sessionStorage、Pinia persistence、URL、日志。
6. Reveal 依次检查 CurrentUser、Resource Scope、ADMIN 或有效 Grant、recent re-auth，再解密和写审计。

建议 C3 增加独立 `resource_credential_reauth_sessions`（或等价命名）表，而不是修改现有 access JWT 或签发长期第二 JWT。

## 6. Audit Reuse

### Current implementation

- `audit_logs` 保存 operator user、action、module、target、JSONB before/after、IP、时间。
- `write_audit()` 与业务变更使用同一数据库事务；查询接口仅 ADMIN / BOSS 可访问。
- 写入和输出都调用通用 `_sanitize()`。
- 当前过滤 password / secret / token / api_key / private_key 等常见键。

### Reuse decision

现有 Audit 模型和事务写入方式可以复用，Credential 不应建立第二套审计系统。建议 `module="resource_credentials"`，target 为 credential 或 grant，仅记录 ID、名称、资源、操作人、动作、时间和非敏感状态变化。

### Mandatory hardening before any secret write

当前 sanitizer 未明确覆盖 `encrypted_payload`、`ciphertext`、`nonce`、`passphrase`、`authorization` 等键。即使 ciphertext 不是明文，也禁止进入 Audit before/after。C1/C2 必须先扩充 denylist，并为凭据服务使用显式 metadata-only audit payload；不能依赖通用对象 dump。

`CREDENTIAL_REVEAL` 和 `CREDENTIAL_COPY` 只记录事件，不记录返回值、复制内容或 payload。Copy 应走独立审计 Action API，不能由纯前端日志代替。

## 7. Notification Reuse

### Current implementation

- 单表 `notifications`，通过 `(type, target_type, target_id, period_key)` 唯一约束实现幂等。
- 支持 generate / refresh / read / resolve。
- PM / MEMBER 的列表通过 `resource_account_id` 接入 `readable_resources()`；ADMIN / BOSS 全局可见。
- 当前 `NotificationType` 只有 RESOURCE_EXPIRING、RESOURCE_EXPIRED、RESOURCE_UNASSIGNED、RECURRING_RULE_DUE。
- 已知冻结行为：任何登录用户调用 refresh 时先全库生成，再按 Scope 返回。

### Reuse decision

C4 可在现有系统中增加 `CREDENTIAL_EXPIRING`、`CREDENTIAL_ROTATION_DUE`，target 指向 credential，同时保留 `resource_account_id` 以复用 Resource Scope。标题和 message 只能使用 resource_name、credential_name、日期/天数等 metadata，绝不能包含 Secret、ciphertext 或 Grant 详情。

refresh 的“全库生成后再过滤”是既有 deferred behavior；凭据提醒接入时必须重新评估其并发、权限和审计影响，但 C0 不修改该行为。

## 8. Backup Reuse

当前 PowerShell / shell 脚本通过 PostgreSQL `pg_dump -Fc` 创建数据库备份，并强制 Restore 到不同于当前数据库的目标库。Gate 6 已验证表行数和 Alembic 版本一致。

现有 DB Backup 可自然包含 ResourceCredential ciphertext，但不会单独备份外部环境中的 master key。这正是所需边界：

```text
DB backup = ciphertext + metadata
master key = 独立 secret 管理与独立恢复流程
```

C5 必须补充真实验证：正确 DB backup + 正确 key 可恢复；错误 key 或缺失 key必须认证失败且不返回部分明文。运维文档必须明确 master key 丢失不可恢复。现有备份文件还可能包含 Audit / Notification，因此必须在 C5 做 dump 明文扫描。

## 9. Encryption Existing

**不存在。** 代码扫描未发现 AES、AES-GCM、Fernet、KMS、EncryptionService、SecretStore、encrypt/decrypt 或 `encrypted_payload` 实现；`backend/requirements.txt` 也没有 `cryptography` 等可用 AEAD 库。

现有 Argon2 只适合不可逆用户密码 hash；现有 PyJWT / JWT secret 不能充当资源凭据加密方案或 master key。

### Recommended Encryption

- C1 增加经过验证的 `cryptography` 依赖，使用 `AESGCM`（AES-256-GCM）；禁止自写密码算法。
- `CREDENTIAL_MASTER_KEY` 使用 base64 编码的随机 32-byte key；源码、Git、数据库、seed、日志、报告均不得出现真实 key。
- 增加显式 `RESOURCE_CREDENTIALS_ENABLED`（或等价开关）。功能启用时，任何环境的 key 缺失、base64 格式错误或解码后不是 32 bytes 都应启动失败；production 绝不能回退到默认 key。
- 存储随机 96-bit nonce 和 AES-GCM ciphertext+tag。可使用独立二进制 nonce 列，或使用有版本的二进制 envelope；不能保存可查询的明文 JSON。
- AAD 应绑定稳定的 credential ID、resource_account_id 和 encryption_version，防止 ciphertext 在记录间被替换。
- `key_id` 只是非敏感标识；`encryption_version` 支持未来迁移。V1.2-M1 只需一个 active key，不实现复杂 KMS。
- InvalidTag / wrong key 统一安全失败，禁止把底层异常、payload 或 key 信息返回 API/日志。

## 10. Resource Scope

当前 `readable_resources()` 真实规则：

| Role / Scope | Resource visibility |
| --- | --- |
| ADMIN / GLOBAL | 全部 ResourceAccount |
| BOSS / GLOBAL | 全部 ResourceAccount |
| PROJECT_MANAGER / MANAGED_PROJECTS | 自己负责项目中存在 active allocation 的资源 |
| MEMBER / MEMBER_PROJECTS | 仅 active allocation 的 `employee_id == current_user.employee_id`，并满足项目为空或项目在本人参与项目内 |

没有 Employee 映射的非 GLOBAL 用户返回空集。MEMBER 不会因为和其他成员处于同一 Project 就看到对方专属 ResourceAccount；这满足跨成员隔离基线。

Credential Metadata 查询必须先 join 到 ResourceAccount 并复用该 Query，不得复制/放宽 Scope。Reveal 必须在 Resource Scope 之后再检查 ADMIN 或有效 User Grant。结论保持：

```text
Resource visibility != Secret reveal permission
ResourceAllocation != Credential Grant
```

## 12. Recommended Tables

### `resource_credentials`

建议按当前 SQLAlchemy 2 / Alembic / PostgreSQL 风格实现：

```text
id                         integer PK
resource_account_id        FK resource_accounts.id, not null, indexed
credential_name            varchar(200), not null
credential_type            varchar(30), not null
encrypted_payload          bytea, not null
encryption_nonce           bytea, not null (若未封装进 versioned envelope)
encryption_version         smallint, not null
key_id                     varchar(100), not null
status                     varchar(20), not null, indexed
expires_at                 timestamptz/date, nullable, indexed
last_rotated_at            timestamptz, nullable
rotation_interval_days     integer, nullable, check > 0
created_by_user_id         FK users.id, not null
updated_by_user_id         FK users.id, not null
created_at                 timestamptz, not null
updated_at                 timestamptz, not null
UNIQUE(resource_account_id, credential_name)
```

`credential_type` 限定为 USERNAME_PASSWORD、API_KEY、ACCESS_TOKEN、CLIENT_CREDENTIAL、SSH_KEY、OTHER；`status` 只使用 ACTIVE、EXPIRED、DISABLED。`EXPIRING_SOON` 动态计算。物理删除默认不提供。

`expires_at` 的 Date / DateTime 最终选择应与产品语义统一：若只按业务日提醒，优先 Date；若授权/轮换要求精确时刻，则用 timezone-aware DateTime。不要混用 naive datetime。

### `resource_credential_grants`

```text
id                         integer PK
credential_id              FK resource_credentials.id, not null, indexed
user_id                    FK users.id, not null, indexed
can_reveal                 boolean, not null
valid_from                 timestamptz, nullable
valid_until                timestamptz, nullable
revoked_at                 timestamptz, nullable
granted_by_user_id         FK users.id, not null
created_at                 timestamptz, not null
updated_at                 timestamptz, not null
UNIQUE(credential_id, user_id)
```

第一版保持每 credential/user 一条可撤销生命周期记录；重新授权更新该行并写 Audit。Reveal 时同时要求：User ACTIVE、`can_reveal=true`、未撤销、valid_from 已开始、valid_until 未过期。禁止 Employee grant 和 allocation auto-grant。

### C3 re-auth table

建议独立表保存 proof digest、user_id、expires_at、created_at、revoked_at；不保存 raw proof 和用户密码。该表不属于 C1 的 Credential 核心 schema，可在 C3 migration 中加入。

## 13. Recommended Grant Model

Metadata 与 Secret 权限分层：

| Role | Metadata | Reveal |
| --- | --- | --- |
| ADMIN | GLOBAL | 允许，但必须 recent re-auth |
| BOSS | GLOBAL | 仅有效显式 User Grant + recent re-auth |
| PROJECT_MANAGER | readable_resources() 范围 | Resource Scope + 有效显式 User Grant + recent re-auth |
| MEMBER | readable_resources() 范围 | Resource Scope + 有效显式 User Grant + recent re-auth |

Grant 管理只允许 ADMIN。任何 allocation、项目成员关系、角色或 GLOBAL scope 都不能自动授予 Secret。Suggested Users 只能是提示，必须由 ADMIN 人工确认。

## 14. API and Serialization Boundary Recommendation

- List / Detail 使用显式 metadata response schema；任何 ORM 自动 dump 都不允许接触 encrypted_payload。
- Reveal 必须是独立 `POST /api/resource-credentials/{id}/reveal` action。
- Metadata schema 只包含版本要求的 id、resource、name、type、status、expiration/rotation、has_secret、can_reveal、grant_count、timestamps。
- Create / Rotate 的 secret request schema 与 metadata schema 分离；response 永不 echo secret。
- FastAPI 默认 Pydantic 422 detail 可能包含 rejected input。敏感路由必须使用 endpoint-aware validation error sanitizer，删除 `input`，并禁止 request-body logging。
- SQLAlchemy 当前未启用 echo，应用也没有 request-body logging middleware；保持该状态。现有日志 filter 是兜底，不是 Secret 安全边界。
- 前端当前只有 access token 使用 localStorage。Reveal secret 和 re-auth proof 必须只放组件内存，离页立即清理，30–60 秒自动 mask；mask 使用固定长度。

## 15. Security Risks

| Risk | Severity | Required control |
| --- | --- | --- |
| 无现成 AEAD 实现/依赖 | High | C1 引入受维护的 AESGCM 库和 known-secret/wrong-key 测试 |
| Audit sanitizer 未覆盖全部凭据字段名 | Critical before C1 write | 扩展 denylist + metadata-only audit payload + leak tests |
| Pydantic 422 可能回显敏感 input | High | 敏感路由专用 validation error 脱敏 |
| `account_identifier` / `remark` 是可导出、可审计自由文本 | High | 禁止迁移；继续明确不是秘密字段；Secret 只进新模块 |
| access token 当前在 localStorage | Existing baseline | 不扩大；Secret 与 re-auth proof 严禁复用该存储方式 |
| 通用日志 filter 依赖关键词 | Medium | 敏感路由不记录 body；异常只记录安全错误码/metadata |
| master key 丢失即不可恢复 | Critical operational | DB backup 与 key backup 分离并形成双人/受控运维流程 |
| key 错误可能造成批量不可解密 | High | 启动校验、key_id/version、C5 restore + wrong-key fail-secure |
| grant 与 Resource Scope 被错误合并 | Critical | Reveal 强制双重检查并覆盖四角色/跨成员测试 |
| refresh 全库生成的既有行为 | Medium | C4 接入时重新评估，Notification 文本仅 metadata |

## 16. Compatibility Risks

- 不得修改 Role、ROLE_SCOPES、ROLE_PERMISSIONS、JWT、Project / Resource / Expense Scope 或 Statistics。
- 新 API 应复用 CurrentUser 和 Resource Scope，而不是给现有权限表添加 `REVEAL` 并改变全局语义。
- ResourceCredential 与 ResourceAccount 一对多；不要把 `credential_name` 设为全局唯一。
- 不应 cascade 物理删除 Credential/Grant；本版本以 DISABLED / revoke 保留审计链。
- 新依赖会改变 backend image，必须锁定版本并在 C1 执行完整 backend 回归。
- 前端新增入口必须服从 IBM baseline：0 radius、no shadow、no gradient、hairline、dense enterprise layout、IBM Blue；不修改冻结 Dashboard。
- 现有 Export 会导出 Resource `account_identifier`。Credential metadata 本版本没有明确导出需求，应保持不新增 Credential Export。
