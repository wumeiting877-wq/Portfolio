## 2. ADMIN 与双重权限

建议批准的边界：所有 Reveal 必须同时检查当前 User ACTIVE、现有 Resource Scope、凭据 ACTIVE 且未实际到期、有效且绑定当前授权会话的 recent re-auth；非 ADMIN 还必须有有效显式 User Grant。

ADMIN **仅免 Grant**，仍调用 Resource Scope 判定并执行 re-auth。BOSS/GLOBAL、PM、MEMBER、项目成员及资源分配均不自动取得 Secret 权限。目标用户没有 Employee 不等于无效用户；按既有 Scope 判断。

| 主体 | 元数据 | Grant 管理 | Secret Reveal |
| --- | --- | --- | --- |
| 未认证/非 ACTIVE User | 拒绝 | 拒绝 | 拒绝 |
| ADMIN | 现有 Resource Scope | ADMIN + 目标资源 Scope | Scope + re-auth + 可查看状态 |
| BOSS | 现有 GLOBAL Scope | 拒绝 | Scope + Grant + re-auth + 可查看状态 |

## 3. Grant 生命周期（拟审批规则）

以 `(credential_id, user_id)` 保留一条生命周期记录，沿用 C1 唯一约束；目标和授予者均使用 User ID。

- 创建：ADMIN 的资源 Scope 与目标 User ACTIVE/资源 Scope 都通过。已有记录返回 409，不隐式恢复已撤销记录。
- 有效期：timezone-aware UTC 比较；`valid_from <= now < valid_until`，边界不含结束时刻。可空代表无该方向时间界限；完整区间要求 `valid_from < valid_until`，禁止设置已到期结束时间。更新合并原值后再次校验。
- 修改：检查 credential/grant 关联和目标身份/Scope；不得改变 credential_id/user_id。`can_reveal=false` 立即停止授权。
- 撤销：记录 revoked_at，保留行和审计，幂等；不得用普通 PATCH 清除 revoked_at。
- 重新授权：建议独立 ADMIN 显式 re-grant 动作，在同一行更新生命周期与授予者并独立审计。接口是否加入本轮须审批；没有该动作时已撤销行保持撤销，不能通过重复 POST 绕过。
- 每次 Reveal 实时检查 Grant、Scope 和身份；缓存授权结论不能替代数据库检查。撤销与 Reveal 并发以事务锁确定顺序：已提交的撤销之后不允许成功；撤销不得追溯已提交并释放的 Secret。
- 创建/列表/修改/撤销均记录非敏感成功或拒绝事件，禁止嵌套 User、hash 或 encrypted envelope。

## 4. 当前授权会话绑定：关键待决项

实际代码 `create_access_token()` 只有 user_id/username/role/scope/exp，没有 jti 或随机登录会话标识。PyJWT 对 datetime exp 使用秒粒度；相同用户同一秒签发可能得到相同 JWT。**SHA-256(Bearer) 无法独立证明不同登录会话隔离**；User ID、last_login_at、IP/User-Agent 也不能作为唯一授权会话。

必须明确“当前授权会话”含义并选择下列一条，不能把提案作为既有批准：

| 方案 | 可提供的安全语义 | 对冻结边界的影响 |
| --- | --- | --- |
| A：C3 独立凭据授权会话（建议） | 独立至少 256-bit 随机 opaque context；proof 绑定 User + Bearer 摘要 + context 摘要。独立 context 间隔离，包括相同 JWT 下两个 context | 不改变 JWT claims/既有登录返回；新增凭据会话建立流程及专用 Header。需要批准以该 context 定义 C3 当前授权会话 |
| B：每次登录唯一服务器会话/jti | 直接区分真实登录会话，包含同秒登录 | 必须单独批准修改冻结登录/Token 或增加每次登录返回的唯一会话凭证，不在未审批情况下实施 |

方案 A 候选：独立 `POST /api/auth/credential-session`，有效 Bearer + 当前密码经现有 Argon2 验证后创建随机 context，有限期不超过当前 JWT 到期并建议上限 30 分钟。仅一次返回 opaque context，数据库仅存不可逆摘要、User、Token 摘要、有效期、epoch、撤销信息。后续 `POST /api/auth/re-auth` 必须提交同一 Bearer 与 context 并重新校验当前密码。Reveal 必须携带同一 context 和 proof。页面内存保存，不进入 URL、浏览器持久存储、日志、审计。context 也是持有者凭证，窃取 context+Token+proof 的组合不在“只持有 Token”隔离能力内。

**限制：方案 A 区分独立凭据授权 context，不能宣称冻结 JWT 已具备唯一登录会话。若验收要求 proof 严格绑定原始每次登录会话，则必须选 B 或提供既有已批准设计。**

## 5. 二次验证与身份永久失效

proof 用至少 32 随机 bytes 生成，数据库仅存 SHA-256 digest、User、选定会话绑定、created/expires/consumed/revoked 信息和安全 epoch；TTL 为 5 分钟并不超过会话/JWT 到期。密码复用 Argon2 服务。不得使用登录时间作为 re-auth 证据。

Reveal 使用 PostgreSQL 单条条件 UPDATE ... RETURNING 原子消费，条件包括未消费/未撤销、有效期、User、会话、当前 epoch；并发最多一次消费成功。失败没有第二次解密机会；拒绝重放、跨用户/会话、错误或过期 proof。

真实 User 服务有自助改密、ADMIN reset_password、update_user(status) 和 set_user_status 多条写路径。只比较当前 ACTIVE 或密码时间戳不能覆盖“停用后再启用”的旧 proof。

拟采用 C3 专用 User security epoch 辅助表，在任何密码 hash/状态变化时同事务递增并撤销旧会话/proof；再次启用不恢复旧 epoch。建议由独立 PostgreSQL trigger 覆盖 users 相关变更，以免遗漏不同服务和 SQL 写路径；不保存密码/hash。Reveal 与上述更新遵循同一 User 行锁顺序，避免停用/改密与消费竞态。**trigger 会增加既有 User 写入的安全副作用，须明确批准该迁移范围；未批准不得执行。** 可替代为批准后覆盖所有服务入口的同事务 hook，但必须证明没有遗漏写路径。

## 6. Reveal、安全错误与审计

拟独立 `POST /api/resource-credentials/{credential_id}/reveal`，全部身份、Scope、Grant/ADMIN 例外、状态、epoch、session/proof 检查通过后才调用 C1 解密。复用原 AES-256-GCM/AAD、key/version 校验；校验 Secret discriminator 与记录类型一致，严格 allowlist 禁止任何额外字段。六类沿用 credential_secret.py，不返回 ciphertext、nonce、key ID、hash 或内部绑定摘要。

敏感路由成功、401/403/404/409/422/503 和未预期异常均设置 `Cache-Control: no-store`、`Pragma: no-cache`、`Expires: 0`；异常统一安全文字。专用边界覆盖依赖及 validation 异常，禁止异常 traceback 携带密码、明文、proof、Token、Master Key 或 SQL 参数。拒绝不披露对象/用户身份内部信息。

Grant、session、re-auth、Reveal 成功/拒绝与完整性失败使用既有 AuditLog，显式 ID/动作/结果/安全原因码 allowlist。成功 Reveal 必须在 proof 消费及成功审计提交后才释放 Secret；审计失败绝不能返回明文。建议 proof 先以独立已审计事务消费并提交，再解密及提交 Reveal 审计，保证完整性/后续审计故障也不恢复 proof；失败可能烧掉 proof，用户重新 re-auth。事务划分和权限锁定必须专项验证，不能只凭图示认定安全。
