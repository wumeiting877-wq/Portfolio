## 1. C1 Scope

本 Gate 仅实现 Credential / Grant 数据模型、AES-256-GCM 基础、Master Key 配置与启动校验、Audit / Validation / Logging 安全边界、migration、测试和本报告。未实现任何 Credential / Grant / Reveal / Re-auth HTTP API，未实现通知、轮换、导出或前端。

## 2. C0 Baseline Confirmation

实施前确认：development compose 使用 `project_cost_hub:55432`，Alembic 为 `0007_resource_name_unique (head)`，Pilot write disabled。保持 ResourceAccount 业务字段、Scope、Role、JWT、Statistics、Dashboard 和冻结 UI 不变；没有迁移 `account_identifier` 或 `remark`。

## 3. Dependency

新增并锁定 `cryptography==50.0.1`。Backend Docker image 已重新构建；该稳定版本支持当前 Python 3.11，并使用官方 `cryptography.hazmat.primitives.ciphers.aead.AESGCM`。

## 4. Master Key Configuration

新增：

```text
RESOURCE_CREDENTIALS_ENABLED=false
CREDENTIAL_MASTER_KEY=
CREDENTIAL_ACTIVE_KEY_ID=
```

Master key 必须为严格 base64，解码后正好 32 bytes。Key ID 必须为 1–100 位，以字母或数字开头，后续仅允许字母、数字、点、下划线、连字符。没有默认 key，不会自动生成或写入配置。`.env.example` 仅给出空变量和生成说明。

## 5. Feature Flag

Flag 关闭时不要求 key，V1.1 业务与测试可正常运行。Development 当前保持关闭，未向仓库或数据库写入 master key。

## 6. Fail-Fast

`app.main` 创建 FastAPI app 前调用 `validate_runtime_config()`。Flag 开启且 key 缺失、base64 非法、长度错误或 key ID 非法时立即抛出安全配置错误；测试覆盖全部分支及合法初始化。

## 7. Encryption Service

`app/security/credential_encryption.py` 只负责 key validation、固定 AAD、encrypt/decrypt 和安全异常。它不依赖 repository、HTTP、Grant、Role、Scope 或 Audit。错误统一为 `CredentialDecryptionError("Credential decryption failed")`，不暴露 key ID、payload、plaintext 或 InvalidTag 详情。

## 8. AES-GCM

使用 32-byte key 的 AES-256-GCM。`EncryptedCredential` envelope 包含 ciphertext（含 authentication tag）、nonce、encryption version 和 key ID。没有自实现 AES、padding 或 MAC，也没有使用 ECB、CBC、Fernet 或 JWT secret。

## 9. Nonce

每次加密调用 `secrets.token_bytes(12)` 生成随机 96-bit nonce。相同 key、plaintext、AAD 连续加密得到不同 nonce 和 ciphertext，二者均可成功解密。

## 10. AAD

AAD 固定 ASCII 格式：

```text
credential:{credential_id}\n
resource:{resource_account_id}\n
version:{encryption_version}
```

绑定 credential ID、resource account ID 和 encryption version，不绑定可修正的 resource name。测试确认修改 AAD 会认证失败。

## 11. Payload Serialization

内部 discriminated union 限定六类：`USERNAME_PASSWORD`、`API_KEY`、`ACCESS_TOKEN`、`CLIENT_CREDENTIAL`、`SSH_KEY`、`OTHER`。每类 `extra="forbid"`、strict、字段长度受限；`OTHER` 仅允许单一 `secret`，不接受任意深 JSON。序列化使用 UTF-8、key 排序和无多余空白的 canonical JSON。

Python 无法保证 immutable bytes 的 secure erase；实现不额外记录、缓存或落盘 plaintext。该运行时限制保留为 Known Issue。

## 12. `resource_credentials`

表包含要求的 metadata、`BYTEA` ciphertext / nonce、version / key ID、状态、过期/轮换字段、User 审计外键和 timestamptz。约束包括：

- `UNIQUE(resource_account_id, credential_name)`
- `rotation_interval_days IS NULL OR > 0`
- credential type / status allowlist
- FK 到 `resource_accounts.id` 与 `users.id`

没有把 Secret 加入 `resource_accounts`，也没有 cascade delete。

## 13. `resource_credential_grants`

表包含 credential、User、can_reveal、生效/过期/撤销时间、granted-by User 和 timestamps。`UNIQUE(credential_id, user_id)`；grant 主体及授予者均 FK `users.id`，没有 Employee FK、自动授权或 permission evaluation。内部 schema 只序列化标量 ID，不嵌套 User / password hash。

## 14. Migration

新增单一线性 revision：

```text
0007_resource_name_unique -> 0008_resource_credentials
```

仅创建两张 C1 表、index、FK、unique/check constraints。测试库已执行 `downgrade 0007_resource_name_unique` 再 `upgrade head`，均通过；downgrade 只删除 C1 对象。`alembic check`：`No new upgrade operations detected.`

首次写入的安全事务方案已经通过测试：同一 transaction 内先从 PostgreSQL sequence 预留 credential ID，基于该 ID 构造 AAD，再创建完整的 NOT NULL encrypted row，最后 commit。任何异常 rollback，不会写入明文或留下空 payload metadata 半成品。C2 持久化服务必须沿用此模式。

## 15. Audit Hardening

递归、case-insensitive denylist 已覆盖 password/hash、secret、API key、token、private key、client secret、passphrase、ciphertext、encrypted payload、nonce、authorization、reauth proof 和 master key；支持 dict/list/tuple。新增 `credential_audit_metadata()` 明确只选择 credential metadata，禁止 ORM `__dict__` audit。

## 16. Validation Error Hardening

新增 sensitive validation sanitizer；生成未来敏感 endpoint 可使用的 422 detail 时，Pydantic errors 不包含 rejected `input`、context 或 URL，敏感字段 message 归一化。Known-secret validation test 确认 rejected value 不在安全响应中。

## 17. Logging Boundary

应用没有 request-body logging middleware；Uvicorn access log 不记录 body；SQLAlchemy `echo` 未启用。日志 redaction token 已扩展到 private key、passphrase、encrypted payload、ciphertext、nonce、master key 和 re-auth proof。Sanitizer/filter 仅是兜底，未来敏感路由仍必须排除 body。

## 18. Plaintext Test

在隔离 test DB 创建 ResourceAccount 和两条 ResourceCredential，使用固定明显假 Secret `V12_C1_KNOWN_SECRET_9X7K`。直接 SQL 读取 `encrypted_payload` / `encryption_nonce`，均不包含明文。Development 表为空，明文扫描结果为 0。

## 19. Tamper Tests

以下全部 fail secure：wrong key、修改 ciphertext、修改 nonce、修改 AAD。对外异常仅为 `Credential decryption failed`，不包含 plaintext、key ID 或 payload。

## 20. Resource API Regression

`ResourcePublic` schema 不包含 `credentials`、ciphertext 或 nonce；现有 Resource responses 不变。ResourceAccount 的现有列未新增 Secret；新 relationship 不触发 Pydantic unrestricted serialization。Resource create/update/allocation/detail/export 测试包含在完整回归中并通过。
